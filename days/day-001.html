1. Deep Architectural Mechanics: AWS Organizations

Account Separation Rationale (The SRE Blast-Radius Principle)

Enterprise workloads must never share an AWS account. Running production and non-production workloads in the same account introduces critical operational vulnerabilities:

  • Hard API Quota Exhaustion: AWS service quotas (e.g., EC2 RunInstances rate limits, KMS cryptographic operations per second, NAT Gateway bandwidth) apply per account per region. A runaway load test or batch worker in a development environment will throttle API calls in production if hosted in the same account.
  • IAM Blast Radius: Over-permissive IAM roles or credential leaks in testing environments can lead to data exfiltration or destructive changes in production.
  • Consolidated Billing & Cost Allocation: While AWS Organizations aggregates volume tiering discounts across all accounts to the Management account, cost allocation tags and Cost Explorer granularity require separate account boundaries for clean chargebacks.

Production Multi-Account OU Topology

The AWS Well-Architected Framework recommends a standardized set of core and workload OUs:

Organizational Unit (OU) Contained Accounts Architectural Function & SRE Guardrail
Security OU Log Archive, Security Tooling Immutable aggregation point for CloudTrail logs, AWS Config recorders, GuardDuty delegated administrator, and Security Hub findings. Root credentials stored in corporate physical vault.
Infrastructure OU Network Hub, Shared Services Hosts AWS Transit Gateway, Direct Connect Gateways, Route 53 Resolver endpoints, and centralized egress inspection VPCs. No customer applications run here.
Workloads Prod OU App1-Prod, App2-Prod Strictly guarded production workloads. Zero interactive developer access. All deployments occur via automated cross-account CI/CD pipelines.
Workloads Non-Prod OU App1-Stage, App2-Dev Staging and development testing. Governed by regional SCPs and resource size limits.
Sandbox OU Developer Sandboxes Unrestricted developer experimentation, strictly isolated from corporate networks with automated 30-day budget alarms and resource termination scripts.
Suspended OU Quarantined Accounts Decommissioned or compromised accounts. SCP attached with an absolute explicit Deny on all actions (*) to prevent any resource launch or egress traffic.

2. Service Control Policy (SCP) Evaluation Mechanics

Crucial Exam Rule: SCPs Never Grant Access

SCPs act as guardrails or perimeter filters. They specify the maximum allowed permissions for an account or OU. Even if an SCP has an explicit Allow for ec2:*, an IAM user or role has zero access until an IAM identity policy explicitly grants ec2:*.

The Five-Layer Effective Permission Formula

For an API call to be permitted in a member account, it must pass through five distinct policy filters:

Effective Permission = (SCP Allow) ∩ (Permissions Boundary Allow) ∩ (Identity/Resource IAM Allow) - (Any Explicit Deny)
  • Default SCP Behavior: Every new Organization attaches the AWS-managed FullAWSAccess policy (Allow * on *) at Root. As long as this remains attached, no actions are blocked by default.
  • Deny-List Strategy (Recommended): Keep FullAWSAccess attached at the Root and all child OUs, and attach custom SCPs containing targeted Effect: Deny statements. Any explicit Deny anywhere in the hierarchy overrides all Allows.
  • Allow-List Strategy: Remove FullAWSAccess and explicitly define allowed services at every level of the OU tree. This requires immense operational overhead and risks breaking newly released AWS features.
  • The Management Account Exemption: SCPs do not restrict the AWS Organizations Management account (root account of the organization) or AWS service-linked roles.

3. DevOps & SRE Cross-Account Automation

Cross-Account CI/CD Pipeline Architecture

In mature DevOps environments, CI/CD pipelines run in a dedicated Shared Tools account and deploy artifacts into target accounts without static credentials:

  1. The CI/CD runner (e.g., GitHub Actions runner or AWS CodeBuild) authenticates via OpenID Connect (OIDC) or native IAM role in the Shared Tools account.
  2. The pipeline calls AWS STS AssumeRole to assume a pre-provisioned DeploymentRole in the target Workload account (Dev/Stage/Prod).
  3. The target DeploymentRole trust policy restricts assumption strictly to the ARN of the pipeline role in the Shared Tools account and enforces external conditions (e.g., repository name, commit tag).
  4. All actions taken by the assumed role are logged in the target account's CloudTrail with the caller identity traced back to the deployment pipeline.

4. Hands-on Implementation Lab

CLI Implementation Walkthrough

  1. Create an Organizational Unit: 
    aws organizations create-organizational-unit --parent-id r-xxxx --name "Workloads-Dev"
  2. Create the Region-Restriction SCP: 
    aws organizations create-policy --content file://region-restriction.json --name "Enforce-US-Regions" --type SERVICE_CONTROL_POLICY --description "Denies all non-US regions except global services"
  3. Attach Policy to Target OU: 
    aws organizations attach-policy --policy-id p-xxxxxxxx --target-id ou-xxxx-yyyyyyyy
  4. Verify Enforcement from Member Account: 
    # Should succeed in us-east-1:
aws ec2 describe-instances --region us-east-1

# Should fail with AccessDeniedException due to SCP:
aws ec2 run-instances --image-id ami-0c55b159cbfafe1f0 --instance-type t3.micro --region eu-central-1

5. Comprehensive SAP-C02 Scenario Practice Questions

Scenario 1: Cross-Account KMS & SCP Interaction
A financial enterprise has an AWS Organizations structure with multiple accounts. The security team manages customer master keys (CMKs) in a dedicated Security Account. A developer role in a Workload Account needs to encrypt and decrypt S3 objects using a CMK in the Security Account. The administrator has attached an SCP at the Workload OU allowing kms:*. The developer still receives an AccessDenied error when attempting to call kms:GenerateDataKey. What combination of actions will resolve this issue? (Select TWO.)
A) Add an explicit Allow statement in the Security Account's SCP for the Workload Account ID.
B) Update the KMS Key Policy in the Security Account to grant kms:GenerateDataKey and kms:Decrypt to the developer role ARN in the Workload Account.
C) Attach an IAM policy to the developer role in the Workload Account allowing kms:GenerateDataKey on the target key ARN.
D) Recreate the KMS key as an AWS Managed Key to bypass cross-account permissions.
E) Disable the SCP on the Workload OU because SCPs block cross-account KMS operations by default.
Correct Answers: B and C.
Architectural Rationale: Cross-account KMS access requires permissions in both the caller's account (identity-based policy, Option C) and the owner's account (resource-based key policy, Option B). An SCP does not grant permissions—it only establishes a permission ceiling. Option A is invalid because SCPs only apply within their own account hierarchy, not cross-account. Option D is false because AWS Managed Keys cannot be shared cross-account.
Scenario 2: Region Containment with Global Services
An enterprise mandates that compute and storage workloads must only be launched in eu-west-1 and eu-central-1. A cloud architect applies an SCP denying all actions where aws:RequestedRegion is not in those regions. Immediately after attaching the policy, global administrators report they can no longer create IAM users, create Route 53 records, or update CloudFront distributions from the AWS Management Console. What is the root cause and how should it be rectified?
A) Global services default to us-east-1. Add us-east-1 to the allowed regions condition.
B) The SCP used an explicit Deny on * without exempting global services. Replace Action: "*" with a NotAction block listing global services such as iam:*, route53:*, and cloudfront:*.
C) The administrators are operating from member accounts. Move the administrators to the Organizations Management account where SCPs do not apply.
D) CloudFront and Route 53 require VPC endpoints. Configure Route 53 Resolver endpoints in eu-west-1.
Correct Answer: B.
Architectural Rationale: Global AWS services (IAM, Route 53, CloudFront, WAF) operate globally or have their API endpoints anchored in us-east-1. When an SCP uses an explicit Deny with StringNotEquals: { aws:RequestedRegion: [eu-west-1, eu-central-1] }, calls to global APIs are evaluated as non-matching and blocked. The Well-Architected solution is to use a NotAction block to exempt all global services from the region restriction.
Scenario 3: Multi-OU SCP Inheritance & Overrides
An AWS Organization has an OU hierarchy: Root → Prod-OU → Finance-OU. An account named Fin-Ledger resides inside Finance-OU.
- An SCP attached at Root has an explicit Deny on dynamodb:DeleteTable.
- An SCP attached at Finance-OU explicitly allows dynamodb:* with a condition allowing deletion only if tagged Environment=Testing.
An administrator in the Fin-Ledger account attempts to delete a DynamoDB table tagged Environment=Testing. What will happen?
A) The table deletion succeeds because child OU policies override parent OU policies in AWS Organizations.
B) The table deletion fails with AccessDenied because an explicit Deny at any level in the hierarchy cannot be overridden by an Allow at a lower level.
C) The table deletion succeeds because tag-based conditions take precedence over unconditional Deny statements.
D) The table deletion fails because DynamoDB table deletion requires root account credentials.
Correct Answer: B.
Architectural Rationale: In AWS Organizations, policy evaluation is strictly hierarchical and additive in restrictions: an explicit Deny anywhere in the inheritance tree (from Root down through intermediate OUs to the account itself) is absolute and permanent. Child OUs can further restrict permissions, but they can NEVER expand permissions beyond what parent OUs allow.
Scenario 4: Delegated Administrator & Least Privilege
A company security policy dictates that the AWS Organizations Management account must only be used for organization management and consolidated billing. Security operations engineers should manage AWS GuardDuty, Security Hub, and AWS IAM Identity Center without accessing the Management account. Which feature should be implemented?
A) Create cross-account IAM roles in the Management account and delegate them to security engineers.
B) Register a dedicated Security Tooling member account as the Delegated Administrator for GuardDuty, Security Hub, and IAM Identity Center.
C) Move the Security Tooling account to the Root of the organization and attach a policy granting management account rights.
D) Use AWS Service Catalog in the Management account to publish security management portfolios.
Correct Answer: B.
Architectural Rationale: AWS Delegated Administrator allows specific member accounts (typically within the Security OU) to administer organization-wide security and governance services without needing administrative access to the Management account, adhering strictly to the principle of least privilege.
