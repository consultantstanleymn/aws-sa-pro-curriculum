1. AWS Resource Access Manager (RAM) & VPC Sharing

VPC Sharing vs. VPC Peering vs. Transit Gateway

AWS RAM enables centralized network management across AWS accounts without duplicating VPCs:

  • VPC Sharing (via RAM): A central Network Account owns the VPC, Route Tables, NAT Gateways, and Network ACLs. It shares specific subnets with participant application accounts via RAM. Application accounts can launch EC2/ECS/RDS instances into the shared subnets. Application teams manage their own Security Groups, while the network team controls IP CIDRs and routing.
  • Security Isolation: Participants in a shared VPC cannot see or modify resources owned by other participants, but can communicate across the subnet via private IP if security groups allow it.
  • Cost Optimization: Eliminates cross-AZ data transfer fees associated with peering or Transit Gateway attachments within the same Availability Zone.

Comprehensive SAP-C02 Scenario Questions

Scenario 1: Centralized Network Architecture with RAM
An enterprise with 50 development accounts wants all applications to reside within high-bandwidth, shared private subnets managed by a central infrastructure team. Applications must be able to communicate with sub-millisecond latency without paying Transit Gateway data processing fees. What is the optimal architecture?
A) Share private subnets from a central VPC to all 50 accounts using AWS Resource Access Manager (RAM).
B) Create 50 separate VPCs and connect them with an AWS Transit Gateway mesh.
C) Create a full mesh of 1,225 VPC Peering connections across all accounts.
D) Deploy AWS PrivateLink endpoints in every account.
Answer: VPC Sharing via AWS RAM allows central network ownership while letting participant accounts launch resources into shared subnets. It completely avoids Transit Gateway processing fees ($0.02/GB) and peering overhead.
